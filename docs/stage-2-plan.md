**Goal (RIGFILE_PLAN.md §12, §8):** `rigfile/base-secure` v1, the always-on safety layer, for Claude Code first. An agent (or human) cannot accidentally commit, read, print or exfiltrate secrets, even when trying, and every rig inherits that.

## What Stage 1 already gives us

## What is new, and the design calls I am making

1. **base-secure is a real rig, embedded in the binary.** `base-secure/rigfile.yaml` (+ files) is `go:embed`-ed, so it works offline, cannot be impersonated from disk, and its version is the binary's version. The resolver uses the embedded copy for `rigfile/base-secure`; the lockfile pins its hash. Updating it = updating rigfile (shown as a normal plan diff). Signed out-of-band updates (`rigfile update`) wait for Stage 6.
2. **Git hygiene is not a manifest category**, it is machine-level git configuration. It becomes a small built-in **host module** (`git`), planned/applied/journaled/rolled back through the same engine and `state.json`, not a new schema section. Its inputs are fixed by base-secure (no user schema surface in Stage 2).
3. **All hook logic lives in Go** (`rigfile hook pre-commit|pre-push|…`); the git hook files are one-line `sh` shims. Stage 3's Windows port only needs the shim.
4. **The scanner is our own matcher over gitleaks' rule data** (ADR 0003, see M1), not a shell-out. Reasoning: gitleaks rules are Go/RE2 already, MIT-licensed, and shelling out costs startup time on every commit and a hard dependency on an external install.
5. **Existing user setup is never clobbered.** The owner already has a global `core.hooksPath` with a dispatcher. The git module *chains*: it installs Rigfile's hooks dir, whose shims run Rigfile's check first, then the previously configured hooks dir's same-named hook, then the repo's own `.git/hooks/<name>` (which `core.hooksPath` would otherwise silence). A user-owned `core.excludesFile` gets a marked Rigfile block spliced in (existing `internal/splice`); only if none exists do we create `~/.config/rigfile/gitignore` and point the config at it. Previous values are recorded in state so `rollback` restores them exactly.
6. **Hard denies live in `permissions.deny`; hooks are the second layer** (already the Stage 1 threat note: Claude Code's Bash matching is best-effort and evadable by obfuscation). The red-team suite measures exactly that gap and documents it rather than hiding it.

## Owner decisions needed (my recommendation first)

- **O1 Scanner approach (ADR 0003):** own matcher over embedded, pinned gitleaks rule data + NOTICE (recommended) vs. importing gitleaks as a library (API stability unverified, heavier dependency) vs. shelling out to a gitleaks binary (not self-contained, slow per commit).
- **O2 False-positive threshold:** recommend ≤ 1% of hard-negative corpus entries overall and 0 on `.env.example`-style files, with every FP listed by rule in the report. I will not tune rules to hit a number without showing you the recall impact.
- **O3 Chaining your existing global git hooks:** recommend chain (yours keep running, Rigfile's runs first). Applying base-secure on your real machine changes `core.hooksPath` and `core.excludesFile`, which I will not do myself; you run `rigfile apply` and approve the plan screen. Alternative: Rigfile-only hooks dir, replacing yours (not recommended).
- **O4 Unpinned MCP servers:** plan §8.3 says every MCP server must be pinned. Stage 1 only warns, and your own `alpaca` entry is deliberately unpinned. Recommend: keep it a plan-screen warning locally, make it an error at `publish` (Stage 4/5), and do not auto-rewrite to a locked version until there is a registry to resolve versions (Stage 4+).
- **O5 Live red-team:** it needs a real Claude Code login and API/subscription usage in a sandbox. Recommend you run the procedure I write (S2-M7(b)); I cannot run it, and pushes/logins are yours.
- **O6 LICENSE (§17 Q1):** still open, and now practical: we would vendor MIT-licensed gitleaks rule data, which needs a NOTICE and a decision on our own licence before the repo goes public.

## Risks

- **Bash matching is evadable.** Denies are pattern matches on command text; `eval`, encodings and indirection can slip past. Mitigation: layered defence (deny + hook + git hooks + pre-push + instructions), an honest evasion table, and never claiming enforcement we cannot show.
- **False positives destroy trust** faster than misses do; hence the corpus, per-rule reporting, and `.rigfile-allow`.
- **Touching global git config** affects every repo the owner has. Mitigation: chaining, journaled previous values, exact rollback, tests on temp homes only, owner applies it.
- **PostToolUse redaction may not be possible** (S2-M0(a)); the plan degrades to documented non-enforcement rather than pretending.
